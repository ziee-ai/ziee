- **DRIFT-1.1** — verdict: none — ITEM-1 landed as planned: `parse_spawn_args` reads `kind` from the top level or from `spec`, honours a nested-only value, and refuses a disagreeing pair (`BACKGROUND_KIND_CONFLICT`). No divergence from PLAN or INV-2.
- **DRIFT-1.2** — verdict: none — ITEM-2's `BACKGROUND_KIND_UNKNOWN` message now names the argument, lists both kinds and carries an example, per INV-1.
- **DRIFT-1.3** — verdict: impl-wins — the plan listed `SPEC_KEYS` for ITEM-3 but did not anticipate that the module's OWN copyable example, `BACKGROUND_SPEC_EXAMPLE`, contained a `"label"` key that no schema declares and no code reads. Under ITEM-3 the example the model is told to copy would have been REFUSED. Resolved by correcting the example to `{"task":"Summarise the attached report"}` and adding an assertion (in TEST-5) that the example survives the module's own rule, so the class cannot come back. PLAN's ITEM-3 wording already covers "the advertisement matches the enforcement"; no plan amendment needed, but the discovery is recorded here because it is a real second instance of the same defect found while implementing the first.
- **DRIFT-1.4** — verdict: none — ITEM-4 landed as `missing_spec_field` + `require_spec_field`, table-driven off `KIND_CONTRACTS`, preserving both existing error codes (`BACKGROUND_TASK_REQUIRED` / `BACKGROUND_COMMAND_REQUIRED`) verbatim.
- **DRIFT-1.5** — verdict: impl-wins — the plan named three helpers for ITEM-5 (`is_known_flavor` / `known_flavor_names` / `validate_flavor`). Implementation added a fourth, `quoted_flavor_names`, because two call sites (the `Some(other)` non-string arms in `resolve_spec_flavor` and `resolve_execute_flavor`) build a refusal WITHOUT going through `validate_known_flavor` and would otherwise each re-derive the quoted list — the exact duplication ITEM-5 exists to remove. Additive, same module, no behavioural difference; PLAN's ITEM-5 intent ("no call site can ship a weaker check than its siblings") is upheld more completely, not less.
- **DRIFT-1.6** — verdict: impl-wins — the plan's ITEM-6/ITEM-7 said "validate `flavor` against `KNOWN_FLAVORS`". Implementation ALSO refuses a supplied non-string and a supplied empty/whitespace string rather than falling back to `minimal`. The plan did not state this; INV-2 requires it ("a supplied-but-undecodable argument is never turned into the default"), and the pre-existing chat-path code let `flavor: ""` through to the sandbox verbatim. Recorded as impl-wins with the invariant as the justification; asserted by TEST-8 and TEST-10.
- **DRIFT-1.7** — verdict: none — ITEM-8 delegated both pre-existing scans with their error codes and message text unchanged; TEST-16 (`INVALID_FLAVOR`/400) and TEST-17 (the `{names:?}` rendering) pin both contracts.
- **DRIFT-1.8** — verdict: none — ITEM-9 strips the consumed `spec.kind` before persistence; TEST-3 asserts it is gone and that every other key survives byte-identically.
- **DRIFT-1.9** — verdict: impl-wins — not in the plan: `common/tool_args.rs` gained `pub fn type_word` (made public, previously private) and a new `truncate_for_message` + `MAX_ECHOED_VALUE_CHARS`.
